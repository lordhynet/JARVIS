# Learning mutation measurement boundary

The opt-in `Measure_training_correction_deletion_and_rebuild_with_unrelated_learning_state` case measures the existing cohesive training correction/deletion path before changing its persistence boundary. It introduces no application behavior, table, service or migration.

Each size has1,000/2,000/10,000 learning cards, manual review receipts, original creation receipts and retained training attempts, plus200unrelated goals. Training totals include110mutated attempts (55correction/delete pairs), five fixed eligibility/order sentinels and the explicitly reported remaining unrelated attempts. Thus even the largest fixture stays within the existing10,000training-attempt bound. All IDs/text are synthetic. Background workers are disabled and connections pooled on disposable test databases.

Five warmup pairs precede50measured pairs. Every correction uses a distinct existing assessed attempt/new operation ID, and every deletion affects a distinct active attempt. No seed/reset occurs in the timed sections. Their projection inputs evolve: each pair invalidates one canonical assessment and deletes another; no attempt reaches the five-answer-version limit. The separately timed rebuild callback repeats an already-current projection. Its full transaction time is reported separately from the pure in-callback projection time, and must not be described as a new mutation or an optimized path. Output reports raw samples, nearest-rank p50/p95 and max, dataset/final counts and synthetic lineage IDs.

Shared functional assertions also run in a normal in-memory test: exclude two already-absorbed baseline reviews, exclude stale-text/deleted/skipped/unscored assessments, preserve later original practice time and sequence ordering, retain manual scheduling, reject conflicting operation replay, preserve original creation receipts, and clear deleted answer/assessment text. A further fixture assertion checks London calendar scheduling across the spring DST boundary after removing the later manual review. Existing real endpoint/concurrency/restart tests remain in the standard suite.

Opt in through the established isolated measurement environment: JARVIS_TEST_POSTGRES and JARVIS_PERF_TEST_POSTGRES must point to the owned disposable loopback test server; JARVIS_PERF_OUTPUT names the generated JSON. Use the shared heavy-gate workflow. CI intentionally skips this fact while running the ordinary fixture and all existing regressions. Completed sizes are written incrementally so a later failure does not erase earlier results.

The existing less-than50ms target remains unchanged. Actual measured results and exact source belong in the review packet; this test does not assert machine-dependent latency, declare the broad runtime gate passed, or implement an optimization. A scoped write or further extraction requires a reviewed dependency/lock/replay/privacy plan based on the measurements. Preserve one canonical projection/history/sequence namespace, original interview coaching, global budget and audio-only Android. No provider or device call is involved.

The rebuild callback explicitly hydrates its existing cold/learning units before starting the pure timer. Hydration remains inside the full transaction timer. Without that step, first lazy property access would incorrectly label database/JSON loading as pure projection work. Neither timer includes a fixture reset or seed.

Phase attribution uses the existing CoreTelemetry.StoragePhaseDuration histogram. Four fixed nested categories delimit cold hydrate, learning hydrate (including validation/snapshot), cold serialization/hash and learning diff. The test-only listener correlates only measured correction/deletion/rebuild scopes through AsyncLocal; it ignores warmup/setup/verification/unrelated work and accepts only fixed categories and finite nonnegative durations. No resource IDs or payloads are added to production tags. Instrumentation overhead is included. Nested timings overlap existing callback/serialize_after stages and must not be summed as disjoint totals; save still combines SQL effects. Separate explicit hydration stopwatch arrays provide a cross-check inside the idempotent rebuild timer. Actual output validates one sample per expected nested phase and operation.
