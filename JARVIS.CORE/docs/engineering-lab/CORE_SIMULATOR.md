# Core payment-queue teaching model

The Lab simulator is a pure, bounded algorithm inside Core. It models fake integer-minor-unit payments, an outbox publication, worker delivery, ledger posting and acknowledgement faults. It uses no runtime state, storage, real money, AI, network or provider budget. It creates no learning cards, personal history, identity or scoring authority. This slice exposes no HTTP/companion endpoint or native client. Tablet decisions and future authorization are separate reviewed work.

Engine `payment-queue-v2` replaces the unmerged v1 algorithm. Every state transition runs through one queue ordered by tick and insertion sequence. Timeline snapshots are captured at the actual transition, with pending broker copies counted separately from future API/ack events. Output is never sorted after snapshots are taken. SplitMix64 and integer amounts are pinned in tests; no framework Random is used.

Each payment has a strict lifetime delivery budget: 1–10 attempts including duplicate copies. Queued copies reserve budget, and a failed earlier delivery can reuse a remaining queued copy instead of scheduling beyond that bound. A persistent poison fault uses Attempt1. DLQ membership is unique per payment. A successfully committed payment can still appear in DLQ after its final acknowledgement fails: the acknowledgement failure does not undo the commit. The expected ledger total counts each committed or non-dead-lettered logical payment once; unsafe repeated posts still violate the double-post and total invariants. This deliberately bounded model does not claim to reproduce a production broker's delivery, cancellation or transaction semantics.

Inputs allow 1–50 payments, 1–10 attempts per payment and at most 50 distinct faults, targeted within bounds. The same seed/request/version yields the same run. Contract snapshots copy the input fault list. Protected records, owner content, canonical learning/replay, retention, cloud consent and existing budget policy remain unchanged. No owner-entry, hardware, deployment, volume or performance acceptance is implied.
