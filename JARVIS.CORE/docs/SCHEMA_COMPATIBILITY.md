# Core startup and schema compatibility

Development-only prerequisite. The reviewed release0.3 deployment/rollback/return scripts predate this command. They must explicitly migrate with the matching binary after stopped-writer backup and before writers start, verify compatibility, and pass an isolated rehearsal before deploying this guard or any extraction. Existing historical release evidence is not a rehearsal of this source. No live release or recovery scripts were run by this change.

Normal PostgreSQL Core startup verifies that every applied migration is known to its assembly and every assembly migration is applied. Either mismatch fails before HTTP serving or hosted workers start. The check shares the existing database migration advisory lock, so startup waits for an in-progress designated migration before checking its committed history. The former `Jarvis:MigrateOnStartup` setting no longer enables automatic migration, including when explicitly true.

On a stopped-writer, backed-up database, an operator runs the same build with `dotnet Jarvis.Api.dll --migrate-only` (or the published executable with `--migrate-only`). It reads the existing canonical configuration, requires PostgreSQL, takes the migration lock, rejects unknown history before changing anything, applies known migrations and verifies compatibility. It exits without starting HTTP listeners or workers. Start the normal Core process only after successful completion. This command grants no authority to deploy or touch live data by itself.

For the existing Compose installation, `scripts/migrate-schema.ps1` uses the existing private configuration/environment helpers, refuses a running API container in its project, prepares PostgreSQL and the intended image, and invokes that one-off command without publishing API ports. It never starts the normal API. The operator must also stop writers outside that Compose project and verify the backup. `-NoBuild` uses the already-built image; schema compatibility must still pass. The isolated deployment rehearsal script now bootstraps through the same explicit command before starting its disposable API.

Tests create owned disposable databases and initialize their schema explicitly. Legacy upgrade fixtures migrate their seeded old snapshots before starting API hosts. The large opt-in measurement harness also initializes outside its measured operations; this does not constitute a new performance result.

This is a startup prerequisite, not a complete mixed-binary runtime fence. It cannot change already-shipped binaries lacking this guard, and it does not stop a process that was already running before a schema change. Before canonical training extraction, establish a guard-bearing supported/rollback baseline and mechanically prevent unguarded writer access. Keep stopped-writer, backup, exact-source review and lossless Up/Down/re-Up requirements. Do not claim that this prerequisite alone closes the old-writer gap or authorizes a live migration.
