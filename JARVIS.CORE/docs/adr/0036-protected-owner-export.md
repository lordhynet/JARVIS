# Authorized protected revision export

Extend JARVIS's existing whole-Core privacy export, not a second Forge export service or history. The optional ForgeProtectedRecords collection contains every retained revision from both encrypted tables, original owner/programme/record/epoch/request/revision/timestamp metadata, and the known versioned business payload. No keys, cipher material or retry MACs are exported. Empty collections are omitted to preserve legacy shape. Payload JSON uses the protected codec's existing property names/schema, while the outer API export retains its existing JSON conventions.

Memory uses its existing privacy boundary. PostgreSQL reads both named shared-type sets inside the same repeatable-read snapshot as the privacy epoch and remaining Core data; no runtime writer lock or new table is added. A request already reading a pre-erasure snapshot can finish with that complete historical snapshot; it must never mix old protected history with a new epoch or erased canonical data. Subsequent exports see erasure. Export is read-only.

Every envelope is opened using its original ValueContext and retained key ID, strictly decoded by kind and supported payload version, and projected only for the authorized response. Historical values are not normalized against today's time, programme, active registry or numeric/unit rules. Missing key fails the whole request503; corrupt/unrecognized data fails it409 rather than dropping fields or returning a partial export. Projection completes before the endpoint returns its object; response serialization does not stream partially validated private records. Generic errors contain no values or key material.

The existing privacy.manage policy remains mandatory: separate owner credential for trusted non-browser owner requests, fresh scoped elevation for enrolled owner browsers, never companions. The response is an explicit attachment with no-store/no-cache. The protector's private configuration adapter reads ProtectedRecords:ActiveKeyId and retained ProtectedRecords:Keys; absent/empty defaults remain unavailable. Export does not require an active writing key when the original retained key is available. Never generate defaults or use recording keys as fallback. No live key/configuration change is part of this implementation.

Managed typed strings and the export JsonElement copies are private request-scoped memory; ADR0032 G1 remains in force. They must not be reused for logs, agents/providers, events, caches, screensaver/watch snapshots or generic displays. Raw decryption buffers remain inside the cleared borrowed reader; the transport projection is deliberately authorized plaintext, not a privacy-class downgrade.

Review X1 bounds this in-memory operation to1024 protected revisions and32MiB padded plaintext (AES-GCM ciphertext has identical length). PostgreSQL preflights count/size in the same snapshot before fetching encrypted rows; memory/shared projection enforce the same bounds before decoding. Excess fails the whole export413 generically. These limits cover protected records, not unrelated legacy Core export. Future streaming/paging needs measured justification and whole-export integrity.

Review X2 adds private-plaintext sensitivity/storage-advice schema fields when protected records exist, plus browser guidance to store the plaintext file encrypted. Empty exports omit these optional fields. Passphrase encryption is deferred. X3: export exactly retained revisions; when retention lands, add removal/remaining-revision tests before entry. No revision retention policy is invented here.

Initial PostgreSQL fixtures exposed an existing atomic-write defect: DbSet.Local includes tracked rows of the shared CLR type without distinguishing named entities. Staged latest/request reads now filter ChangeTracker metadata against the selected named set. Memory/PostgreSQL regressions stage check-in/capacity with identical record/request IDs in one transaction, with independent later revisions. No new identity or receipt store.

This is export support, not an owner entry feature. D1 operational database-plus-active/retained-key recovery, bounded owner commands and scope/source resolution, applicable step-up and retention remain entry/release gates; green synthetic tests do not satisfy D1. Existing interview programme, learning/replay, agents, budget and audio-only Android are unchanged. Independent exact-source review and green CI precede merge; deployment remains separate.
