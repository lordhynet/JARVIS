# Hot runtime rows inside D2

The existing IRuntimeStore and D2 transaction remain the application boundary. PostgreSQL moves audio lease/drain/fence, single-use voice tickets and voice turns out of RuntimeDocuments into RuntimeAudioState, RuntimeVoiceTickets and RuntimeVoiceTurns. The privacy gate and the existing runtime document FOR UPDATE lock still serialize writers across hosts. The move changes storage, not ownership, lease duration, transcript consent, budget policy or erasure rules.

The first measured split still read/wrote 1.14 MB of cold state for a control toggle and missed the 50 ms gate. RuntimeHotControlState therefore also moves the four small audio/authentication control collections (AgentControls, Devices, DeviceCredentials and WakeCandidateAttempts) to JSONB columns on the existing singleton hot row. Runtime locks select only Id/Fingerprint; cold properties hydrate together on first access inside that transaction. Their getters and setters load before use, so replacing one cold collection cannot discard the others. Hot-only updates neither transfer nor serialize the cold document. This is storage hydration, not a second orchestration or memory engine. Cold financial/artifact updates still pay the existing document cost.

Lease/ticket state is small and loaded with each callback. Voice turns hydrate only if the callback accesses them, using the same open context and transaction. Identity snapshot reads materialize before closing the context. Callbacks must fully materialize returned projections, as they already must not defer a state mutation or perform network I/O. Unrelated updates do not load transcripts. Transcript edits currently hydrate the collection for compatibility with existing Dictionary callbacks; each save writes only changed rows. This first slice does not claim indexed per-turn reads throughout every service.

Cold state uses a canonical dictionary order and a persisted SHA-256 fingerprint, avoiding a second pre-callback serialization once initialized. JSONB key normalization cannot create false dirty writes. Hot records compare against captured values; no-op and lease-only changes do not rewrite the cold document. All writes, including canonical session messages, remain atomic under D2. Audio invalidation is signalled only after commit.

Voice rows have a session/time index and preserve the original timestamp representation alongside PostgreSQL's microsecond timestamp. This retains legacy sub-microsecond precision and offsets used by provenance hashes. Transcript text, locked provenance and optional timing are unchanged. Retention, export and erasure hydrate and mutate these same tables in their privacy transaction; they are not a second memory store.

The two additive migrations backfill existing values before removing hot properties from the JSON document. RuntimeHotRows runs before RuntimeHotControlState. Invalid dictionary identities fail migration rather than silently losing a turn. Downgrade reconstructs the current JSON from hot rows before dropping columns/tables. Stop all Core writers, take a verified database backup, apply both migrations and start matching binaries. For rollback stop writers, migrate down through both to LockedVoiceHomeGrants with matching new tooling, then run the old binaries. Do not run old and new binaries concurrently across this storage migration. No live migration was applied during development.

Synthetic performance results must identify sample counts, workload, pooling and host conditions. The gate is runtime update p95 below 50 ms on the recorded harness, with wake-to-ticket reported separately. An in-process Core measurement excludes actual microphone/wake recognition, phone transport and a paid provider connection; it is not end-to-end hardware acceptance.
