# Enrolled browser and short owner elevation

Browser enrollment extends DeviceCredentials, the existing registered-device identity and privacy epoch. The owner explicitly enrolls a browser using the separate owner management credential. Only a credential minted for the owner-browser purpose authenticates to owner browser policies. Device kind, display capability and browser tags never upgrade an ordinary companion credential. Ordinary native enrollments retain their existing limited policies.

The browser keeps its scoped credential in this tab's session storage, supports manual reconnection and clears it on explicit disconnect, credential refusal or erasure. A credential-copy button supports owner password-manager storage for reopening a closed tab. Owner keys and elevation tokens stay in memory. Sensitive operations use a random five-minute elevation bound to the browser credential hash, privacy epoch, owner-key fingerprint and an installed scope allow-list. One hashed elevation is stored on the existing DeviceCredential record; minting replaces the previous elevation and adds no second credential store or migration. Minting requires the separate owner key; presenting that key directly to a sensitive endpoint cannot bypass browser elevation. Revocation, rotation, expiry and erasure invalidate further authenticated requests. This is credential-based enrollment and step-up, not WebAuthn or hardware-backed attestation. Existing exact action approvals and device grants remain necessary.

The legacy shared key is accepted by default. Authentication:RequireEnrolledBrowser=true explicitly refuses the legacy key and legacy hub tickets. Enroll and verify a browser before enabling it, retain a protected operator recovery route to configuration and test reconnection. No private configuration is changed by this implementation. Data erasure destroys browser identities, so recovery requires temporarily disabling this flag, rotating the legacy Core key, reopening with the separate owner credential and enrolling again before re-enabling it.

Single-use hub tickets retain their short lifetime and bind enrolled browsers to their actual credential and epoch instead of silently promoting them to legacy owner identity. Session-event publication and Web Push select active owner-browser fingerprints alongside the optional legacy identity; native fingerprints are excluded. Revoked identities stop receiving future event/push dispatch. Neither the URL nor logs contain a reusable credential. Owner elevation is not embedded in hub tickets. Requests are authorized at validation time; revocation does not claim to cancel an external operation that has already been accepted under a valid exact approval.

Erasure/reopen always bind the recovery fingerprint to the configured Core key, including erasure initiated by an enrolled browser. A browser credential cannot accidentally satisfy the required Core-key rotation. The operator temporarily disables the enrollment-only flag for recovery as described above.

This remains a single-owner deployment. It does not add multi-user isolation, OIDC, a new policy engine or third-party identity traffic. The migration flag remains off by default and was not changed on a live host. Browser credentials are secrets, and a compromised same-origin script can use the active tab's authority; normal script and TLS protections remain required.
