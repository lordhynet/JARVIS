# Quoted recording transcription in the existing import store

Date: 19 November 2026. Track R2. No new provider, model, rate card, package or configuration key.

## Confirmation and accounting

An unlocked manual owner requests a quote for the recording's current revision. A quote lasts ten minutes and binds its ID, reviewed configured transcription model/rate and uploaded capture pieces. Nothing is sent by quotation, page load, refresh, restart or an agent. The first dispatch requires explicit cloud consent and confirmation of that exact quote. The dashboard may advance subsequent pieces only after successful responses within this owner-confirmed quote; any failed/unknown response stops its sequence. Reload does not resume paid work.

Each piece is claimed durably before reserving through the existing UsageBudget ledger. Its maximum preserves the existing transcription calculation: ceil(seconds) / 60 × reviewed USD-per-minute rate × 2. The quoted GBP bound is checked again against the actual reservation before dispatch. Reservations use the existing interactive lane, OpenAI provider identity, pause controls, account/environment scope and GBP ceiling. The production adapter reuses OpenAiProvider's existing multipart request/gateway with an in-memory canonical WAV, avoiding the generic upload path's plaintext temporary decode files. Pricing/model/key readiness comes from the existing reviewed configuration; routing and rates are unchanged. With no granular provider billing, the conservative reservation remains committed; it is not described as measured actual spend.

Operations have stable identities. A lost response or duplicate request cannot replay its provider call. Preparing/running state survives restart; an owner can classify an attempt left in flight after ten minutes as uncertain, with no redispatch. Unknown provider outcomes retain their charge and set reconciliation-required, blocking further paid reservations. Continuation requires the existing verified billing reconciliation (including its ten-minute in-flight guard) and another explicit owner confirmation. It skips the failed piece and processes only unattempted pieces. Failed pieces are never automatically retried. This iteration does not offer a manual paid replay of a failed piece.

Privacy/deletion is checked before dispatch and again before saving the result. A late response cannot recreate a deleted recording, transcript or erased Core. Confirmed monetary reservations may survive as existing accounting records. If no request was dispatched, a failed preparation releases its reservation and pauses rather than retrying. A price change requires a fresh quote; reconciliation can still clear old outcomes before obtaining that new quote.

## Pieces, speakers and honest timing

R1's canonical capture chunks are at most 60 seconds / 1,920,044 bytes, below both the existing 10 MB upload cap and existing three-minute decoded-duration cap. R2 transcribes those existing boundaries individually. It does not claim ten-minute batching, AAC conversion, silence segmentation or a new acoustic timestamp capability. This provides bounded memory and deterministic recovery without decoding dependencies. Large archives are processed as multiple bounded pieces; no oversized archive is uploaded as one request.

Windows labels each transcription by its independent `user`/`interviewer` capture track and merges by start time. The microphone and loopback intervals can overlap. Android begins as `unknown`; the owner can label a segment Me, Interviewer or Unknown with a transcript-revision check. Capture provenance stays unchanged when its speaker label changes. A phone segment may contain multiple speakers; the owner should leave it unknown when it cannot be assigned reliably. There is no automatic diarization, voice identification or voice cloning.

The existing configured text transcription returns text, not word timestamps. Segment intervals therefore describe capture chunks, not the exact words' onset/end. The stored/public timing source says this explicitly. Pace from a chunk interval is an estimate; acoustic pauses are unavailable. Partial captures, failed pieces or a later reported capture discontinuity retain a partial transcript label. Real question/answer alignment and precise acoustic timings are not claimed from these intervals.

## One transcript store and privacy

Successful text goes straight into the existing consent-gated interview ImportService store. Recording/job rows contain piece hashes, state, operation/reservation identities and quotes, never a second copy of transcript text. A code-owned internal import path permits overlap between independent capture tracks while retaining ordered non-overlapping intervals within each track. Ordinary external imports retain their original timing rules and cannot supply capture provenance. Recording imports allow up to 500,000 characters within the existing global two-million-character/200-document cap; each piece remains bounded to 10,000 characters. Public ordinary imports retain their 100,000-character cap.

Recording links, partial status and provenance are additive optional JSON fields. Defaults are omitted so legacy serialized imports/segments keep their shape. There is no new relational migration after R1. Existing data is preserved. Delete/retention uses ImportService's purge path; deleted imported text cannot be resurrected by a later transcription result. Successful complete transcription honors delete-audio-after-transcription through the existing recording retention path, with retryable unpaid cleanup if file removal fails. Partial/failed transcriptions keep audio for recovery under R1's retention period.

Interview imports, including older manually imported interviews, cannot become memory, agent context or domain knowledge. Source eligibility and memory creation now enforce this. Interviewer data is for the owner's practice only, sent solely to the configured transcription provider under explicit consent. Preserve these guards when rolling back binaries; do not restore an older import-to-memory policy over recorded interview data. Back up the database, encrypted volume and stable recording key consistently as in the R1 ADR.

R3 question timelines, answer clips and practice remain separate. Physical capture/transcription quality and precise speaker/time alignment require owner acceptance later. All development/provider checks use fakes.
