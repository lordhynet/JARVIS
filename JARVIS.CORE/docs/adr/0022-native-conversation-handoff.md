# ADR 0022: Native conversation handoff

Status: source implementation; physical acceptance remains outstanding.

Core's existing SessionLifecycleService remains the single handoff state machine: checkpoint, target ready, source release, completion. Native clients use one fixed, generated companion route, POST /api/voice/handoff. A paired device can control only its own identity and participating handoff. The route returns bounded transport metadata (opaque session/handoff IDs, expiry, state and eligible peer names), never transcript text, private titles, checkpoints, summaries or tickets. Locked polls expose no peer list or active-conversation selection. Read-only polls do not acquire the runtime write lock.

The owner chooses an exact peer in phone/tray controls, or makes a fresh captured request such as “continue on my phone”. Core's voice tool accepts only the exact bounded phrase and latest unrestricted utterance in a live unlocked window. It refuses ambiguous phone/laptop/browser targets. The tool proposes a move and reports waiting for acceptance; it cannot claim completion. Private interview conversations permit this narrowly guarded transport action alongside coaching; unrelated tools remain refused.

Phone notifications say only “Continue on phone?”. Tapping opens the activity; acceptance requires the unlocked app and normal cloud-voice consent. No remote microphone foreground service is started. A visible connected activity polls for offers; when owner-enabled local wake or live voice is already running, that foreground service also polls. A fully stopped/background app without that service receives no new transport poll until reopened; this change does not introduce push infrastructure or a new background service. Notification/recording/microphone permissions still apply. An Android phone call cannot be recorded by this feature.

Windows uses a tray target list and explicit accept/decline prompt. The tray enables separate metadata monitoring only with the existing cloud-voice consent. The reusable audio controller keeps that monitor opt-in; local wake recognition itself sends no speech or provider request. Revocation/erasure stops monitoring. Target acceptance and Core preparation require an explicit unlocked report, preserving L15A-03 and applying it to incoming phones as well. Lock changes during waiting are refused. Both native clients verify that the prepared/claimed conversation matches the accepted session before starting its audio.

After target readiness, the source cancels voice, stops playback, joins its capture/session shutdown and acknowledges release. Wake is disabled on that source during transfer. Android holds its existing foreground service until this bounded acknowledgement finishes; Windows waits for StopAsync. A failed/uncertain shutdown never acknowledges release. Core moves ownership through its existing lease/fence; the target obtains a fresh single-use ticket through the normal voice path only after transfer. No audio is queued for later replay, no paid call is retried by the handoff coordinator, and preparing/accepting metadata does not itself dispatch a provider call. Recording exclusions continue to prevent voice admission.

Native starts carry stable operation IDs. Core pins the request hash and checkpoint, rejects changed-body reuse and does not duplicate a retried checkpoint. Completed steps may acknowledge delayed duplicates; genuine out-of-order or foreign-device events are refused without advancing state. Decline is idempotent. Existing 30-second expiry and persisted handoff/checkpoint state provide timeout/restart recovery. Loss of a source process can require expiry/cancellation and a new owner move; no client assumes a silent device has stopped on the strength of a network timeout alone.

No new table or migration is needed. Added handoff request fields are optional and omitted at default, preserving old browser requests and persisted JSON. Kotlin DTOs, enums and fixed routes are generated from C# with the existing parity check. The original owner browser routes remain owner-only. No native business dashboard, conversation store, key, provider, model or rate setting is added.

Automated fake transport, locking, restart and browser checks establish the protocol boundaries, not real device/audio quality. Hardware acceptance must still exercise browser→phone, phone→browser and laptop→phone, locked targets, Bluetooth output, a mid-reply source stop, permission denial and network loss. Build artifacts are unsigned review packages; this work does not install or deploy them.
