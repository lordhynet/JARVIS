# Forge encrypted revision storage foundation

ForgeCheckIns and ForgeCapacity refine the two existing table sketches. They share one ciphertext CLR shape mapped as two named EF entities, not a third generic document/receipt table. Each immutable record revision also stores the original encrypted result and keyed retry proof of its save request. The unique request index is scoped to owner/programme/table; the revision key is owner/programme/record/revision. Categories, observations, values, routine blocks and request values have no plaintext columns. Outside the envelope are only opaque identity, revision/epoch, request identity, operational timestamp, key IDs and cipher/MAC material. Database constraints bound envelope sizes/versions and revision relationships; parent FKs cascade.

Existing ICoreTransactionWrites appends and reads ciphertext. Existing privacy SHARE/runtime writer lock coordinates all PostgreSQL hosts and composite session/runtime changes. The held privacy epoch is passed explicitly through both Core and recording transaction adapters. Memory uses the existing privacy boundary, stages writes for rollback, stores the same envelopes and defensively copies mutable ciphertext arrays. Both enforce current epoch, non-deleted parent, expected revision and request uniqueness. Paused owner configuration is editable; no planner, learning or agent is dispatched.

Value AAD uses the stored result revision. Retry context uses a fixed per-kind save-operation purpose and the ORIGINAL stored owner/programme/record/epoch/expected revision. Because the protection primitive requires a positive context revision, expected revision zero maps reversibly to context revision one. Canonical request bytes must also include original request ID and expected revision alongside the normalized business request. A retry looks up its immutable request row, not the latest record; comparison uses that row's stored proof key ID. These low-level ports do not normalize business input, compare a retry themselves or grant authorization. Later typed commands must implement that workflow, retain required old keys and return the original result. No separate idempotency authority is added.

Deleting a programme physically purges every protected revision/receipt in the same transaction, including staged rows. Full erasure clears both tables/collections under the existing exclusive privacy boundary, without needing decryption keys. Existing configuration-only project tombstones remain. Until authorized protected export is implemented, exporting a Core containing protected rows explicitly fails 503 instead of returning a silently incomplete export. Empty downgrade/reapply preserves existing interview/learning/session data; Down refuses non-empty protected tables before dropping either.

This is deliberately unavailable for owner entry: no baseline/capacity endpoint, business handler, protector DI/key configuration, display/AI projection or feature activation is added. Authorized decrypted export/retention, owner step-up scopes and the D1 verified database-plus-active/retained-key restore rehearsal remain mandatory integration/release gates before real owner data. Synthetic storage/decrypt-marker tests do not satisfy operational recovery acceptance. Review R1 applies to future typed readers: decode inside the borrowed span, never copy raw plaintext into retained buffers/logs/events/tasks. Ciphertext copies made here contain no decrypted payload.

E1 explicitly blocks shipping the first real entry endpoint until authorized decrypted export and D1 operational recovery are ready alongside owner step-up and retention. A protected row currently blocks the WHOLE Core export, so the fail-closed foundation is not entry-ready even if keys are configured. Do not weaken this gate to export only the remaining Core data.

E2 adds ForgeProtectedJson at the future typed-command boundary: serialize into an owned bounded writer, limit final JSON to the existing64KiB ceiling, pad with JSON whitespace to512-byte buckets, and pass it to the existing protector. No original-length field or cipher-format/key change. UTF-8 serialization may request worst-case escaping space, so scratch requests are bounded separately to6x64KiB+256bytes; the entire rental is cleared on every exit, including failures. Authorized readers decode directly inside the borrowed span, and valid old unpadded JSON remains readable without rewriting it. Typed commands must still validate bounded domain input and use this codec for every new payload. Bucket/cadence metadata remains observable; exact optional-section sizes within a bucket are hidden, not all size information.

E3 deletion deliberately enumerates both shared-type tables. Per-kind reads/appends must use the named set, never a raw ChangeTracker query without a kind-aware table decision. Memory/PostgreSQL tests use the same record and request IDs in both tables to verify independent read/receipt/revision behavior.

G1 limit: zeroing clears the helper's owned raw buffers only. Decoded payload strings and temporary escaping buffers used internally by System.Text.Json remain in managed memory until reuse or garbage collection; .NET cannot guarantee clearing every copy. Keep typed payloads within the authorized request, never in caches, logs, events or background tasks. G2: protection rents roughly393KiB of serialization scratch at current check-in rates; revisit only with measured bulk-import demand.
