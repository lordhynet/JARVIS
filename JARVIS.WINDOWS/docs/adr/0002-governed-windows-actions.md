# ADR 0002: Bounded Windows execution through existing Core commands

18 November 2026. Item 5, implemented for local verification and source review. Owner approval of the capability list is required before installation.

Extend the existing device capability/grant/proposal/dispatch/receipt chain. Register seven windows.* contracts in the same capability registry used by agents and domains. App, URL and folder arguments contain owner-configured IDs, never executable paths, arbitrary URLs, command lines or scripts. Core constraints and the local owner allow-lists both apply. Known shell/interpreter executable identities are refused even after renaming; an allowed app additionally requires its SHA-256 identity. Apps receive no arguments. File search is read-only, bounded to 5,000 scanned files, recursion depth 8 and 20 result names, without contents or returned paths.

Use the existing unique dispatch request ID as the command fence. Windows capabilities use NeverReplay. Core authenticates the delivery with a domain-separated HMAC over the device, capability/version, argument hash, IDs and timestamps using the scoped credential verifier; HTTPS and device enrollment also apply. The Windows client requires an accepted signed acknowledgement from Core before a native action. Core rechecks the current device grant, proposal, any agent scope, voice audio fence and expiry in that acknowledgement transaction. The shared receipt wire MAC remains compatible. The delivery MAC is credential-bound authentication; the authoritative permission decision is Core's current acknowledgement.

Persist a CurrentUser-DPAPI journal before acknowledgement/dispatch. It binds to the enrollment/privacy identity, retains up to 2,048 command IDs and stops rather than forgetting replay protection at capacity. A crash with an unfinished entry produces an unknown-outcome failure receipt after restart and never repeats the effect. A persisted final outcome can be reported again with the same receipt ID without executing again. This local journal is separate from Core's factual receipt store; it installs no scheduler or policy engine.

Actions have an explicit opt-in and inert local configuration placeholders. Only opted-in actions poll Core; local wake with actions off preserves its no-network-before-wake behavior. Polling stops on credential/privacy/network/journal failures and can be stopped from the tray. Voice Off continues to stop microphone and playback independently.

Only media and workstation lock are permitted while locked. Spoken locked requests also require AllowWhenLocked. Core parses current captured speech and stores its audio fence; a model cannot supply arbitrary executable arguments. App/folder aliases are hidden while locked. File search checks lock state during enumeration and discards results after locking; Core checks the live fence/lock again before returning private results. Expired, cancelled and revoked work cannot obtain current dispatch authority.

File boundaries reject traversal and reparse points, including junctions. Use handle-based normalized final paths and handle attribute tags to check roots and each result; enumerate with reparse points skipped. No network folder roots are accepted. Native junction and renamed-shell fixtures exercise these checks without executing a shell as an action or reading owner files.

OS results are reported precisely. The lock API confirms initiation; a URL launch does not inspect page content; volume-key delivery does not measure the resulting volume; notification submission does not attest visibility. Media uses the Windows session control result. These distinctions remain in receipts and the voice instructions. Hardware acceptance is pending and is not inferred from fake-platform tests.

No new dependency or migration is required: delivery authentication is computed from existing command/grant fields, and short-lived voice authority metadata uses existing runtime JSON with export/retention/erasure. Core hot-runtime persistence remains Item 12. No private configuration, running app, live provider, installation, release image or deployment is changed by this build.

Primary API references checked during implementation:

- [Windows media session controls](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssession?view=winrt-26100) and [uap7 globalMediaControl capability](https://learn.microsoft.com/en-us/uwp/schemas/appxpackage/uapmanifestschema/element-uap7-capability).
- [GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew); FileAttributeTagInfo also checked against installed Windows SDK headers.
- [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) and [LockWorkStation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-lockworkstation).
- Explicit mute uses [SetMute](https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nf-endpointvolume-iaudioendpointvolume-setmute) and [GetMute](https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nf-endpointvolume-iaudioendpointvolume-getmute), with interface order checked against installed Windows SDK headers. It sets mute true and reads the result, avoiding a toggle that could unmute an already-muted endpoint.
